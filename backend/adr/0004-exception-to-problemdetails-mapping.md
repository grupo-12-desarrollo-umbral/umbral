# Domain/application exceptions map to RFC 7807 ProblemDetails through a category-driven handler

Each service (`session-operations-service`, `mission-design-service`, `identity-access-service`) translated unhandled exceptions to RFC 7807 `ProblemDetails` through its own hand-maintained `Api/Services/ProblemDetailsExceptionHandler.cs` switch statement, and the three had drifted: different namespaces, inconsistent `Title` conventions (generic RFC titles vs. full human sentences), only `session-ops` set machine-readable `Type` slugs, `identity-access` routed some validation failures to 422 by **string-matching the message** `"Target user must be active."`, and none exposed the structured FluentValidation `errors` dictionary. The deeper cause: there was **no base exception type** — all ~135 domain and ~13 application exceptions inherited directly from `System.Exception`, so each handler had to name every concrete type, and the handlers named only ~23/37/21 of them. The remaining ~69 domain exceptions silently fell through the catch-all to **HTTP 500**.

This ADR fixes the mapping as a per-service, **category-driven** handler over a compiler-enforced `DomainException` base, so a new exception classifies itself the moment it is declared and can never silently become a 500.

## Status

accepted

## Considered Options

- **Per-service category-driven mapper over an abstract `DomainException` base (chosen).** Three tiny abstractions per service in `src/Domain/Exceptions/` — `ErrorCategory` (a transport-agnostic enum, no HTTP in the Domain layer), `IErrorMetadata` (the `{ Category, ErrorCode }` contract the handler matches on), and `DomainException` (abstract base whose `Category` is **abstract**, forcing every subtype to classify itself at compile time). The handler matches the `IErrorMetadata` interface, never concrete types, so it is identical across all three services. The actual failure mode — a silent 500 on a new exception — is prevented **structurally**: you cannot compile a new domain exception without giving it a category.
- **Extract a shared kernel** (one `ErrorCategory`/`IErrorMetadata`/`DomainException`/handler library consumed by all three services). Rejected for now. The repo has no solution (`.sln`) files — each service compiles in isolation — and each `Dockerfile` build context is its own service folder with `COPY src/ ./src/`, so a project living outside the service folder would be **outside the Docker build context** and image builds would fail. Sharing would require re-rooting every build context (and rewriting the Dockerfiles) or publishing a versioned internal NuGet package — non-trivial infra changes. `CONTEXT-MAP.md` and the ADR series also define these as deliberate DDD bounded contexts, where a shared kernel is a governed coupling point, not a default. The shared types are tiny and change rarely; the only real cost of duplication is drift, and the abstract `Category` compile-check removes that cost. See the revisit trigger in Consequences.
- **Keep enumerating concrete exception types in each handler (status quo).** Rejected: this is exactly what produced the drift and the ~69 silent 500s. Every new exception silently regresses to 500 until someone remembers to add a handler arm; nothing makes the omission visible.

## Consequences

- **Category vocabulary.** `ErrorCategory` is the transport-agnostic semantic vocabulary: `NotFound | Validation | Conflict | Forbidden | Unauthorized | Unprocessable`. It lives in the Domain layer and carries no HTTP knowledge; the HTTP mapping lives only in the API-layer handler.
- **Category → HTTP status / generic title** (the single table, identical in all three handlers):

  | Category | Status | Generic Title |
  |---|---|---|
  | `NotFound` | 404 | `Resource not found.` |
  | `Validation` | 400 | `Validation failed.` |
  | `Conflict` | 409 | `Conflict.` |
  | `Forbidden` | 403 | `Forbidden.` |
  | `Unauthorized` | 401 | `Unauthorized.` |
  | `Unprocessable` | 422 | `Unprocessable entity.` |

- **Slug convention.** `IErrorMetadata.ErrorCode` is a stable, machine-readable kebab-case slug emitted as the ProblemDetails `Type`. `DomainException.ErrorCode` auto-derives it from the type name (`InvalidSessionStateTransitionException` → `invalid-session-state-transition`) by stripping the `Exception` suffix and kebab-casing; a subtype overrides the property only to preserve an existing published slug. Application-layer exceptions implement `IErrorMetadata` directly with a hardcoded category + slug. The common app slugs are `not-found`, `validation-failed`, `forbidden-access`; reuse them if you add app exceptions. The **preserved override slugs** (so existing clients keep working) are, in `session-ops`: `invalid-state-transition`, `mission-not-eligible-for-session`, `trivia-substage-empty`, `session-no-teams`, `session-operator-unassigned`.
- **The uniform handler.** A four-arm switch: `ValidationException` → 400 with the structured `Extensions["errors"]` dictionary; any `IErrorMetadata` → `StatusFor(Category)` + `Type = ErrorCode` + `TitleFor(Category)`; `System.UnauthorizedAccessException` → 401 (`unauthorized`, the one framework type that can't implement our interface); everything else → the 500 fallback (`internal-error`). `Detail` is always `exception.Message`, so the full human message is preserved even though `Title` is now generic. The handler body is byte-identical across the three services (mission-design's namespace was corrected from `Web.Services` to `Api.Services` to make this true).
- **No-silent-500 guarantee, locked two ways.** The abstract `Category` is the build-time half (an unclassified exception fails compilation). A per-service reflection coverage test is the runtime half: it reflects over every concrete `DomainException` subtype, runs the real handler, and asserts a non-500 status matching the type's category plus a non-empty `Type` slug.
- **SignalR shares the same source of truth.** `session-ops`'s `DomainExceptionHubFilter` derives its `HubException` code from `ErrorCategory` (`NotFound→NOT_FOUND`, `Validation→VALIDATION_FAILED`, `Conflict→CONFLICT`, `Forbidden→FORBIDDEN`, `Unauthorized→UNAUTHORIZED`, `Unprocessable→UNPROCESSABLE`) instead of a parallel hand-maintained map, killing the second drift surface and the old blanket `_ => "ERROR"` swallow. Five finer-grained UPPER_SNAKE codes (`LATE_JOIN_NOT_ALLOWED`, `PARTICIPANT_REMOVED`, `WRONG_TEAM`, `ALREADY_CONNECTED`, `TEAM_UNAVAILABLE`) stay as explicit overrides — they are a published mobile contract (`mobile/src/lib/realtime/reconnect-policy.ts` parses them by regex) and are emitted byte-identically to before.
- **identity-access 422 string-match removed.** The `"Target user must be active."` pre-check in `AssignUserRoleCommandValidator` was redundant: `User.AssignRole` already throws the domain `DeactivatedUserRoleAssignmentNotAllowedException` (Unprocessable → 422). The validator block and the `IsUnprocessableRoleAssignment` handler arm were deleted; the 422 now comes from the typed domain exception. (`User.AssignRole` was reordered to check `!IsActive` before the unchanged-role short-circuit, so assigning a deactivated user even their current role still throws 422.)
- **Shipped contract changes (clients should branch on `Type` and read `Detail`, never `Title`).** `mission-design` `Title`s changed from human sentences to generic category titles (the sentence still lives in `Detail`); all services gained a stable `Type` slug and a structured `errors` dictionary on validation responses; ~69 exceptions moved from 500 to real 4xx. One deliberate status change: `MissionNotReadyForActivationException` moved **400 → 409** (per the "not-ready-to-activate gates → Conflict" rubric, consistent with the sibling trivia publish gates). To revert it, flip its `Category` to `Validation` and the two corresponding test assertions.
- **Frontend/mobile consumer audit (done, no client changes required).** Per `CONTEXT-MAP.md`, the API-contract change was audited against `frontend/` and `mobile/` before shipping. Findings: the frontend already branches on the stable `Type` slug where it needs a specific cause (`createSession`, `transitionSessionState`), and its two `Detail` substring checks (`team is not active`, `already associated`/`scheduled`) read `Detail`, which is **unchanged** (still `exception.Message`) — so they continue to match. No frontend code reads `Title`; none asserts HTTP 500. The mission activate 400→409 change degrades gracefully because the frontend surfaces `Detail` verbatim on both branches. Mobile consumes only its own `code`/`message` body and HTTP status, not RFC 7807 fields, and is unaffected.
- **Revisit the shared-kernel decision** if the repo later adopts a repo-root Docker build context, a multi-service solution file, or an internal NuGet feed. At that point `ErrorCategory`, `IErrorMetadata`, `DomainException`, the handler, and the common app exceptions are the natural first extraction; until then they stay duplicated per service.
