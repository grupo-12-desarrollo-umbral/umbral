# Historias de Usuario UMBRAL — Versión Mejorada

Este backlog está organizado por secciones para seguir un flujo más natural del producto: primero acceso y permisos, luego diseño de contenido, preparación de sesiones, ejecución en vivo, flujos específicos de misión/QR y trivia, y finalmente puntaje, ranking y auditoría.

> Nota de alcance: Las historias del baseline académico cubren el PDF del Proyecto Integrador UMBRAL UCAB. Las historias de Trivia, QR y cliente móvil de participantes en React Native corresponden a extensiones comprometidas en el roadmap del equipo y deben defenderse como refinamientos sobre el mismo backbone de sesiones, equipos, evidencias, puntaje, ranking y auditoría.
>
> Restricciones explícitas de alcance:
>
> - La plataforma solo soporta los modos `Trivia` y `TreasureHunt`.
> - Cada sesión pertenece exactamente a uno de esos dos modos.
> - No se soportan sesiones híbridas ni una jerarquía configurable de flujo.

## Notas técnicas asociadas al backlog

- La autenticación se implementa con Keycloak/OIDC según el roadmap.
- Las actualizaciones en tiempo real se implementan con WebSockets/SignalR.
- Las consultas se implementan separadas de los comandos para cumplir CQRS/MediatR.
- Los cambios relevantes de sesión, evidencias, puntajes, penalizaciones y eventos de auditoría deben poder publicarse como eventos de dominio para procesamiento asíncrono mediante RabbitMQ.
- RabbitMQ se usa para procesos secundarios como auditoría, notificaciones, consolidación histórica, alertas, recálculos no críticos o soporte a proyecciones.
- Debe existir al menos un workflow RabbitMQ demostrado de punta a punta, por ejemplo `EvidenceSubmissionRegistered` publicado después del éxito transaccional y consumido por auditoría/historial, notificación y recálculo secundario o soporte de proyecciones.
- El flujo principal de juego no debe depender de RabbitMQ para aceptar evidencias, cambiar estados críticos o actualizar el puntaje inmediato de una sesión en vivo.
- Docker Compose, cobertura de pruebas, arquitectura hexagonal y CI/CD se documentan como requisitos no funcionales o tareas técnicas, no como historias de usuario.
