## Known quirks / gotchas

- **The throw-vs-record boundary is the design crux — flagged for Stop 1.** HU-29's structural intake links **throw** (→ RFC-7807, no record): a submission with no resolvable `(session-admits, team-in-session, active-substage)` context cannot be *constructed* (base ctor guard + `bd_umbral_entity_spec.md:446`), so those stay throws — and they are exactly what lets AC #5 "preserve session, team, substage" hold (the context must resolve before a record exists to reject). HU-30's `EvidenceValidationPolicy` covers the **softer, form-agnostic contextual rules** whose failure yields a **recorded** rejection: active-substage/`MissionNode` binding of the *declared* node, temporal window, origin. Partition of AC #2/#3's checks: session-admits / team-in-session / **participant membership** / active-substage-**pointer-resolves** = HU-29 structural throws (each already shipped — `SessionAdmitsReceptionLink`, `GetTeam`, `RuntimeParticipationLink`, `ActiveSubstagePresentLink` — and each is a precondition to *construct* the record, so a failure cannot "preserve" the context AC #5 requires); node-**binding** (the declared node ∈ the resolved active substage) / temporal window / origin = HU-30 recorded rejections. **Membership and team are throws, not recorded rejections** — putting a membership/team link in this chain would be dead code, because the facade runs the intake throw before the contextual policy (verified against `DependencyInjection.cs:70-73` + `EvidenceIntakeFacade.cs`). Migrating any structural check from throw to recorded-rejection would change HU-29's shipped behavior — **do not** do so without explicit Stop-1 sign-off (see the session-state audit note below).
- **Trivia observable behavior must not change.** The only concrete form today (trivia) already enforces membership/participation as throws (`SubmitTriviaAnswerCommandHandler.ResolveParticipantId` + `RuntimeParticipationLink`), and its late/duplicate rejections are **form-specific throws** owned by HU-34 (`LateTriviaAnswerException`, first-write-wins) — HU-30 leaves those untouched (AC scope note: "Las reglas específicas de cada forma … permanecen en HU-31 y HU-34"). HU-30 is an **additive substrate**: the recorded-rejection outcome is genuinely *exercised end-to-end by the QR form (HU-31)*, which routes its contextual failures into `Reject(reason)`. For HU-30, the recorded-rejection path is proven at **domain + application + integration** level (a contextual link failing marks the base record `Rejected` and persists it with a reason), not through a new endpoint and not by converting any trivia throw. Gate every touched span with **all HU-34/HU-29 trivia tests green**.
- **Facade ordering + AC #1 is in-memory, single-commit.** "Register `Pending` before evaluating result" (AC #1) does **not** mean a separate persist before validation: `RegisterEvidenceCore` constructs the base record in `Pending` **in memory** and raises `EvidenceSubmissionRegisteredEvent` (`LiveSession.cs:517-540`); the facade does a **single** `UpdateAsync`/commit at the end (`EvidenceIntakeFacade.cs:33-41`). So the flow is: structural intake chain (throw) → construct base `Pending` in memory → `EvidenceValidationPolicy` (contextual) → on failure `Reject(reason)` / on pass → form-specific validation + accept → **one** commit. A contextual failure therefore commits **one** `Rejected` row (not a separate pending row then a rejection); AC #6 holds because the registered fact is raised in memory and rides that single commit. This reorders "construct `Pending`" ahead of "form validation" relative to HU-29's current `RegisterAsync`. Treat the exact seam (facade signature split vs. an added policy step) as a Stop-1 implementation decision; the invariant is *contextual policy runs on the constructed pending record before form acceptance, trivia behavior unchanged*.
- **Session-state is a throw, not a recorded rejection (residual product call).** RB-03 calls session-state failure a "rechazo", but the entity-spec wording is *negative* — "submissions **cannot be accepted** when `Paused`/`Finished`/`Cancelled`" (`bd_umbral_entity_spec.md:448`) — which a throw satisfies (never persisted ⇒ never accepted); and `Finished`/`Cancelled` sessions have no active-substage pointer, so a rejected record could not even "preserve substage" (AC #5). HU-29's shipped `SessionAdmitsReceptionLink` throw is the canon-correct default and stays. The one alternative that would flip this: if the product wants blocked-while-`Paused` submissions **persisted for the operator audit trail** (RF-09 / `EvidenceReviewQueueProjection`, `bd_umbral_entity_spec.md:931`) — ADR-0010:50-52 puts operator review out of first-delivery scope, so the default is throw; flag for Stop-1 sign-off only if audit-history of paused submissions is desired.
- **`EvidenceSubmissionRegistered` is the registration fact, not the outcome.** It already fires at pending registration carrying `Pending`; HU-30 does **not** change its payload to the final state and does **not** add `Accepted`/`Rejected` events (no transport, no in-scope consumer — result query is HU-32). AC #6 ("published for accepted *or* rejected evidence") is satisfied because rejected evidence is registered-`Pending` first, so the fact fires, and the transaction **commits** (persisting the rejected record) rather than rolling back.
- **`rejectionReason` needs a migration.** Unlike HU-29's `Pending` (a string-compatible enum value on the existing `validation_state` column), `rejection_reason` is a brand-new nullable column on `live_session_trivia_answer_submissions` (and, later, the QR table) — `ef migrations add` **will** report a real diff. Do not skip the migration.
- **Reviewer fields are HU-32, not here.** `reviewedByUserId` / `reviewedAt` (`bd_umbral_entity_spec.md:432-433`, RF-09) are the *operator manual review* fields — HU-30's rejection is **automatic/contextual**, so it sets only `ValidationState = Rejected` + `RejectionReason`. Do not add reviewer fields.
- **Namespace is `umbral_backend.*`** across all session-ops layers (`umbral_backend.Domain.*`, `umbral_backend.Application.Sessions.*`); the Application DI file uses `Microsoft.Extensions.DependencyInjection` by convention. Match existing files. Registration order in `DependencyInjection.cs` **is** the chain run order — add the new links there, do not edit chain classes.
- **Policy naming.** The matrix and DDD model name the pattern `EvidenceValidationPolicy` (`required_patterns_matrix.md:123`, `ddd_solution_model.md:442`); `bd_umbral_entity_spec.md:913` names the domain policy `EvidenceAcceptancePolicy` — two names for the same acceptance/rejection responsibility. Realize it as the application chain `EvidenceValidationChain` in `Sessions/Common/EvidenceValidation/` (mirroring the `EvidenceIntakeValidation/` convention) and cite the canon policy name.
